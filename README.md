# Product Job Map

The job atlas is GradBuddy's grounding layer: live job postings from the Fortune 500, venture-backed startups and the
employers MBA students target, read against one skill taxonomy into role graphs, plus the Spring 2027 course registry.
The site is four verbs behind a door (PLAN.md, "The four verbs behind a door (v19)"). The door (`#/`) is a welcome
screen that takes an email and what the person studies; everyone can skip it, and a Cornell NetID address opens Find
classes. Home (`#/home`) is the four verbs, which are also the top bar. **Find jobs** (`#/jobs`) is one search over
every open US posting of both role sets, with counted facets and, with a résumé on file, "N of the M skills this
posting asks for are on your résumé". **Explore careers** (`#/skills`) is a launcher by field or search
into the role pages and the fit screen, with the résumé's match on the side. **Find classes** (`#/classes`) is the
Spring 2027 picker on two public files, no sign-in anywhere, matching each class to the roles chosen. **Networking**
(`#/network`) says who to meet for a role, where to find them and what to say, with a prep card per chat. Every path
that promises more ends in a coming-soon box that takes an email. The atlas states facts and matches; it runs no model
at runtime, and nothing a person uploads leaves their browser.

One thing on the site is private: the **apprentice map** (`#/map`, PLAN.md v20), a skill tree per class of roles and a
quest map of missions, generated by hand in `../GradBuddy Project/gradbuddy/apprentice/` for one invited person and
published to a private bucket under their user id; the person signs in with a magic link (`#/signin`, sign-ups off)
and Build skills opens the map first. Everyone else sees the free tier and one line, "Have an invite? Sign in."

See [PLAN.md](PLAN.md) for the design and [docs/GRADBUDDY_CONTRACT.md](docs/GRADBUDDY_CONTRACT.md) for what another program (GradBuddy) reads from the atlas: the files, the functions, their shapes and ids, what is stable and what is not, and the privacy rule.

## Run it

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # requests, beautifulsoup4, pypdf, psycopg
.venv/bin/python -m pipeline.backlog pull   # the raw postings from the Supabase backlog -> data/raw/jobs*/ (SUPABASE_DB_URL in .env)
./run_all.sh            # merge registry, scrape (cached per company), extract, build graph; log in logs/run_<date>.log
./run_all.sh --refresh  # fetch every board again and merge into the backlog (--force is the old name)
.venv/bin/python -m pipeline.scrape --roles mba --refresh   # weekly: the MBA backlog (several hours; add --ats workday or --only "Name" to narrow)
.venv/bin/python -m pipeline.discover --from 101 --to 250   # (re)discover careers sites for a rank range
.venv/bin/python -m pipeline.scrape --rank-from 101 --rank-to 250   # scrape one Fortune tier
.venv/bin/python -m pipeline.scrape --roles mba   # same companies plus role-specific employers, the MBA roles -> data/raw/jobs_mba/
.venv/bin/python -m pipeline.extract --roles mba  # tag the MBA postings -> data/processed/jobs_mba.json.gz (about 20 minutes)
.venv/bin/python -m pipeline.build_graph --roles mba  # the MBA graph -> web/data/graph_mba.json + web/data/graph_mba/<role>.json
.venv/bin/python evals/run_pipeline.py            # evals for titles, levels, countries, golden postings and the graph files
.venv/bin/python evals/run_depth.py               # content evals for the published skill depth (style, specificity, evidence, build steps)
.venv/bin/python -m pipeline.funnel --from 2026-10-31 --to 2026-11-07   # the capture funnel: sessions, the share reaching each screen, cohort applications by source; then the journey: drop-off by day and screen, calls to action shown/clicked/done, returns, visible time (CAPTURE_DB_URL in .env); --notes adds each applicant's sentence
node evals/lines_judged.mjs --dry-run             # a model reader judges 50 generated fit-page lines (OPENROUTER_API_KEY in .env for the live run); report in evals/lines_judged.md
.venv/bin/python -m pipeline.runs --last 20       # the last recorded runs of every stage, on any machine or runner (SUPABASE_DB_URL in .env)
gh workflow run refresh-mba.yml                   # the weekly MBA refresh, by hand (also: -f ats=workday, -f only="Accenture", -f trial=true, -f dry_run=true)
gh workflow run refresh-product.yml               # the monthly product refresh, by hand
.venv/bin/python -m pipeline.catalog_export        # the Spring 2027 catalog -> web/data/catalog/cornell_tech.json (public) + web/data/local/catalog_full.json (this machine)
node pipeline/catalog_tags.mjs                       # skill tags per class code -> web/data/catalog/cornell_tech_tags.json; rerun after a taxonomy change
.venv/bin/python -m pipeline.jobs_open               # every open US posting of both role sets -> web/data/jobs_open.json + jobs_meta.json (after build_graph; run_all.sh and the workflows run it)
.venv/bin/python -m pipeline.map_publish <slug> <email>   # one student's apprentice map (gradbuddy/apprentice/, map.json) -> the private `maps` bucket under their user id (CATALOG_SERVICE_ROLE_KEY in .env)
.venv/bin/python -m pipeline.map_feedback [<email>]        # the feedback files the students wrote on their cards, per student
cd web && python3 -m http.server 8000   # then open http://localhost:8000
```

## Hosting

The site is the `web/` folder as it is: no build step, every path relative (`data/…`, `tokens/…`), a hash router
(`#/…`) that needs no rewrites. Any static host serves it. The host is the Vercel project `gradbuddy-atlas` (https://gradbuddy-atlas.vercel.app, created 2026-10-31 on the `wk332` team)
linked to this GitHub repository: root directory `web`, framework preset
"Other", build command empty, output directory empty. Production deploys from `main`; every pull request gets a
preview URL. `node --test tests/web/assets.test.mjs` checks that every local script and stylesheet `web/index.html`
names exists on disk and that the remote scripts pin a version, so a deploy cannot ship a tag that points at nothing.
`web/data/local/` (gitignored) is never hosted.

One serverless function rides along: `web/api/infer.js` (`POST /api/infer`, Vercel picks up `api/` under the root
directory; `web/vercel.json` bundles the taxonomy files it reads and allows 30 s). It sends the resume text, once
per upload, to Claude Haiku 5.5 for the skills it shows without naming them, and stores nothing; it needs
`ANTHROPIC_API_KEY` in the project's environment variables and answers 503 without it, when the site reads the
patterns alone. `CONFIG.INFER_ENABLED` (web/config.js) turns the call off. The local python server has no `/api`, so
a local run reads the patterns alone; the eval is `node evals/infer.mjs` (evals/README.md, "The model read"), run
over the whole external résumé set (`pipeline.store pull evals` first), never the eight samples alone (CLAUDE.md).

## A fresh machine

```bash
git clone git@github.com:wfkhan97/product-role-atlas.git && cd product-role-atlas
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env                              # fill in the keys you need; each comment says which command reads it
.venv/bin/python -m pipeline.store bootstrap      # the raw postings backlog (both role sets), the sample resumes, the model caches
.venv/bin/python -m pytest tests/python && node --test 'tests/web/*.test.mjs'
```

Everything git ignores and a pipeline step needs lives in the Supabase project: the raw postings in the
`backlog_files` and `postings` tables (`pipeline.backlog`), the rest in the private `atlas-store` bucket
(`pipeline.store`), one store per kind: `evals` (`evals/resumes/external/`, the published sample resumes the
calibration reads, and `evals/resumes/private/`, the real ones), `caches` (`data/experiments/` except `scratch/` and
`_trash/`: the model answers of `depth_gen`, `build_steps`, `role_corpus`, `skill_audit` and `decisions_audit`) and
`logs` (`logs/`, pushed by the scheduled jobs). `push <store>` uploads what changed and never deletes a remote file;
`pull <store>` writes what differs and never overwrites a local file newer than the store's copy (it prints those);
`status` counts both sides; `--only PATH` narrows a push or a pull. Without `SUPABASE_SERVICE_ROLE_KEY` every store
command says so and exits 0, so a checkout without secrets still runs the tests and the evals.

## Where secrets live

`.env.example` names every key the code reads and the command that needs it. The values are in two places and
nowhere else: the repository's GitHub Actions secrets for the scheduled jobs (`.github/workflows/`), and the owner's
password manager for the Macs, copied into `.env` (gitignored) by hand. Never in a commit, a doc, a log
(`pipeline/log.py` masks the `.env` values in every line) or a chat.

## Tests and logs

`node --test 'tests/web/*.test.mjs'` checks the browser code and `.venv/bin/python -m pytest tests/python` the
pipeline (`pip install -r requirements-dev.txt` once); both finish in about a second and never touch the network.
`tests/README.md` says what a test is and what an eval is. Every stage logs through `pipeline/log.py`: INFO lines
per stage with counts and elapsed seconds, WARNING for a skipped record or a partial fetch, ERROR with the traceback
for a failed employer, all on stderr; stdout stays as it was. `./run_all.sh` also writes the log to
`logs/run_<date>.log` (gitignored) and prints the path at the end; any stage does the same when `PIPELINE_LOG` names a
file, and `PIPELINE_LOG_LEVEL=DEBUG` shows more. API keys never appear in a log line: the values in `.env` are masked.
Every run also writes one row: when `SUPABASE_DB_URL` is set, `log.setup` installs a recorder that, as the stage's
process ends, inserts into the `runs` table (`pipeline/sql/002_runs.sql`, applied once by the owner) the repo, job
(`PIPELINE_JOB`, else the stage), stage, host, start and end, whether it was ok (no ERROR line, no uncaught
exception), the counts of the stage's summary line, the WARNING and ERROR tallies and the log file's path; nothing in
a row is content. `PIPELINE_RUNS=off` turns it off (the tests set it). `.venv/bin/python -m pipeline.runs [--last 20]
[--job NAME]` prints the rows as a table.
CI (`.github/workflows/ci.yml`) runs both test suites, `node evals/run.mjs` and `evals/run_pipeline.py` on every pull
request and on `main`.

## Scheduled jobs

Nothing that runs on a schedule depends on a Mac being awake. `.github/workflows/refresh-mba.yml` runs the MBA
refresh every Sunday at 03:17 New York on GitHub-hosted runners, one scrape job per ATS family (each pulls the
backlog, scrapes its family with `--refresh --ats <family>`, pushes each file to the backlog as it is written and its
log to the `logs` store), then one job that pulls the backlog back, re-extracts, rebuilds the graph, runs the checks
CI would run and opens a pull request from `data/mba-<date>` with the changed `data/processed/` and `web/data/`
files, which the job merges itself when the pipeline evals and every CI check pass in the job (a failing run opens a
draft the owner reads; the repository variable `REFRESH_AUTO_MERGE` set to `off` leaves every pull request open).
`refresh-product.yml` does the same for the product set on the first Sunday of the month. No job pushes to `main`
except through that merge. The scheduled runs go ahead only when the repository variables `REFRESH_MBA_SCHEDULE` and
`REFRESH_PRODUCT_SCHEDULE` are `on`, set after the runner trial (`evals/runner_trial_2026-10-26.md`, filled by
`evals/runner_trial.py` from the logs); a family a hosted runner cannot reach runs on a self-hosted runner on the
Mac mini (`docs/SELF_HOSTED_RUNNER.md`). Secrets come from the repository's Actions secrets ("Where secrets live").
`python -m pipeline.runs` shows every run's row.

## Scratch versus documentation

Interim work (plans under review, mockups, audits) lives under `data/experiments/scratch/<topic>/` (gitignored) or the
session scratchpad, never in the tree; `./sweep_scratch.sh --go` moves it to `data/experiments/_trash/<date>/` at the
end of a thread. What lasts goes here (what exists, how to run it) and in `PLAN.md` (the decisions and why). The rule is
in `CLAUDE.md`.

## Layout

- `pipeline/adapters/` — one module per ATS (Greenhouse, Lever, Ashby, Workday, Eightfold, Phenom, Oracle HCM, SmartRecruiters, Amazon, Apple, Google). Two adapters read boards that only the MBA employers use. `talnet.py` reads tal.net (Oleeo) boards from their public Atom feed (`…/candidate/jobboard/vacancy/<n>/feed/structured`, the whole board in one answer). A firm has several boards (experienced hires, students, regions), so the config names them: `{"host": "lek.tal.net", "boards": [{"name": "Americas", "path": "appcentre-2/brand-2", "vacancy": 3}, …]}`. When the firm puts the description in the feed (CohnReznick) it is taken from there; otherwise each vacancy page is read (L.E.K.). Some tal.net sites put their vacancy pages behind a captcha (Evercore): the adapter does not pass it, says so on stderr and returns nothing for those postings. `yello.py` reads Yello (recsolu.com) boards (Kearney): the board page names its search URL, the search answers 25 cards a page, the whole board is listed and filtered by title, then each job page is read; the list shows an age or a day without a year, so `posted` is approximate. Configs for both are in `data/raw/registry_mba_employers_talnet_yello.json`.
- `pipeline/roles.py` — which titles count as product roles; family / level / specialisation classification. Seven families: the six of v5 and `product_engineer` (2026-10-30: "Product Engineer", "AI Product Engineer", "Forward Deployed Engineer", the builder role between product and engineering). A product engineer title that names a hardware discipline is dropped (`HARDWARE_RE`); a bare one is settled by its posting text at extraction (`software_build`: a stack, a repository or an AI coding tool against drawings and the plant). The scrape's searches are `SEARCH_QUERIES` in `pipeline/adapters/common.py`.
- `pipeline/taxonomy.json` — the skill taxonomy (clusters, skills, regex patterns): one vocabulary for every role set. A skill marked `"only": ["mba"]` belongs to that role set alone; unmarked skills are shared. A shared skill may carry `"patterns_for": {"mba": [...]}`: stricter wording for that role set, where a word that means the skill in product postings is said in passing. `pipeline/tax.py` hands each role set its part, and `build_graph` writes the product part to `web/data/taxonomy.json` for the web app and the evals. Patterns are tuned for precision against model judgments on a 200-posting sample (see `evals/extraction_baseline.md`); avoid bare everyday words. Every skill also carries a `kind` (`pipeline/tax.py`, `KINDS`): `method` (a craft with an artefact: PRDs, valuation, S&OP), `practice` (work through people: stakeholders, programmes, partnering), `behaviour` (asked by every field, shown through other work, never named: communication, ownership, influence), `technical`, `knowledge` (industries and rule sets), `tool`, `credential`. The kind says nothing to extraction; it decides how a resume shows the skill and how the interface should treat it.
- `pipeline/evidence.json` — how a resume shows each of the 278 skills, hand-written: the `form` (`through` other work, `scope`, `artefact`, `outcome`, `built`, `context`, `named`), the `artefacts`, `counterparts`, `measures` and `verbs` a line that shows it carries, and `shown_by`, the concrete skills whose evidence counts for a behaviour or a practice (every behaviour and every practice names some, since v16 step 6; `evals/run_taxonomy.py` holds each to the postings). `pipeline/fields.json` — what the 24 skills that four or more of the 11 fields ask for mean in each field that asks: `reads_as` (one sentence), `shown_by` (the field's own skills that carry it; each must co-occur with the skill in at least 15% of the field's postings that ask for it) and `line` (one resume line in the field's words, with a number). A key `role:<role id>` beside the field keys is a role override with the same shape, for a role whose field reading does not fit it (M&A integration, Corporate development, Treasury, Commercial banking RM; PLAN.md v16 step 6), grounded on the role's own postings; the screens and the matcher read the override before the field's entry (`tax.field_keys`, `Atlas.fieldKeys`). `tax.validate` checks both files; `evals/run_taxonomy.py` checks them against the postings. The graph build publishes `kind`, `how_shown` and `fields` on every skill node (the field entries with the postings' own carriers and sub-skill mix beside them) and the kinds table in `meta.kinds`.
- `pipeline/depth/*.json` — editorial depth per skill: plain-English definition, sub-skills (with regex patterns and examples), a four-step level ladder, how to build it, and resume lines that show it. Sub-skills are also tagged in postings and used for partial credit in the matcher. The product files were written by hand. The MBA files (`mba_*.json`) are written by `pipeline.depth_publish` from posting evidence: `ladder` is keyed by industry ladder first (`{"bank": {"associate": ..., "mid": ...}}`, corporate, bank and consulting rungs differ), `build` by ladder too (`{"bank": [{kind, text, target, source, url, grounding, demand}]}`), and `provenance` holds, for every statement, sub-skill and step, the posting ids, employers, quoted phrase and cited sentences it rests on, and the reason of every empty rung. A rung that the postings do not support is absent, never padded; a ladder with one rung is not shown. The skill card on a role screen shows the role's own industry ladder, with that ladder's level names; when it is not written for the skill, another industry's, labelled as such. `mba_roles.json` holds per role and ladder the licences, exams and degrees that five employers name at entry level (`asks`) and the steps a source grounds (`build`); the graph build copies them into `roles.<role>.depth` of the index.
- `pipeline/scrape.py`, `extract.py`, `build_graph.py` — the three stages. `scrape`, `extract` and `build_graph` take `--roles product|mba`; scrape and extract share one code path (title filter, cleaning, repost and repeated-URL dedupe, tagging in worker processes). The web app is product-only for now. Extract also pulls evidence sentences per skill and level group; build_graph computes the axis positions (seniority = share-weighted level centre of mass; IC vs leads-teams = director+ share vs staff/principal share; commercial vs technical = PMM/growth share vs TPM/platform share), rank-spread with shrinkage for rare skills.
- `data/raw/fortune500_2026.json` — the 2026 Fortune 500 with Fortune's industry labels; `pipeline/sectors.json` groups those 66 industries into 11 sectors for the Industry filter.
- `pipeline/discover.py` — automatic careers-site discovery for Fortune companies (domain via Clearbit/Wikipedia, careers-link crawl, ATS signature detection, Workday tenant guessing, adapter verification). Output in `data/raw/discovery/`. Companies it can't resolve are handed to research agents, whose results land in `data/raw/registry_fortune_agents_*.json`.
- `pipeline/verify_one.py` — verify a single ATS config with the real adapter.
- `data/raw/funds.json` — the 52 venture funds (institutional, corporate and YC) whose portfolios feed the startup side; `data/raw/portfolio_<fund>.json` are the scraped portfolio lists (name, website, status, stage where the fund states it).
- `pipeline/probe_startups.py` — for every active portfolio company, finds a Greenhouse / Lever / Ashby board (slug guessing plus a careers-page scan), keeps those with product postings, and writes `data/raw/registry_startups.json` with each company's list of backing funds. Stage: fund-stated Seed/Series letters are kept; otherwise it is inferred from the company's own postings ("we raised our Series B") in `pipeline/extract.py`.
- `data/raw/registry_*.json` — per-company ATS configs; `pipeline/merge_registry.py` merges them (hand-verified > agents > auto) with Fortune tier, industry and sector into `data/registry.json`. One job board is one employer: startups that fund portfolios list under two names are merged (other names kept in `also_listed_as`).
- `data/raw/jobs/*.json`, `data/raw/jobs_mba/*.json` — raw postings per company. Each file is a backlog, not a snapshot: a refresh never drops a posting. One the board still shows gets a new `last_seen`; a new one is added with `first_seen`; one the board no longer shows gets `closed` (the day we first missed it). A posting is its requisition id (`external_id`), or its URL on a board that gives none: Bank of America puts a per-session token in every job URL, and a retitled or moved requisition gets a new URL, so the URL alone is not stable. One that comes back takes the board's current title, URL and text. A fetch is incomplete when a listing page could not be read, a search ran into its page cap (the largest employers' searches do), or it returned under 30% of the postings that were open. An incomplete fetch closes nothing by absence: each open posting that did not come back is asked about one by one (the adapter's `still_open`, checked first on three postings that did come back), and only one the board says is gone is closed; the file says `partial` with the counts. Lever, Greenhouse and Ashby return a whole board at once and have no check. `pipeline.scrape --refresh --recheck-closed DATE` also asks, on an incomplete fetch, about postings closed since DATE and reopens the ones still shown (closures before 2026-10-29 treated a capped search as complete). For the MBA set a closed posting stays in the statistics for 12 months after it was last seen (`KEEP_CLOSED_DAYS` in `pipeline/extract.py`) and carries `open: false` into the graph, so the interface can leave it out of listings. The product set drops closed postings until its interface can hide them.
- `pipeline/backlog.py` — the store of the raw posting files: the `backlog_files` and `postings` tables of the GradBuddy Supabase project. `data/raw/jobs/` and `data/raw/jobs_mba/` are not in git (over 350 MB together, and every refresh rewrites every file; the history before 2026-10-19 still holds them). `push` sends the files (the scrape pushes each file as it writes it when `SUPABASE_DB_URL` is set), `pull` writes them back byte for byte, `verify` proves the round trip, and a full scrape keeps the newest four dated gzipped snapshots in the `backlog` storage bucket. Push never deletes a posting and pull never overwrites a local posting the database lacks. `.env` holds `SUPABASE_DB_URL` (session pooler) and `SUPABASE_SERVICE_ROLE_KEY` (snapshots). A fresh machine runs `pull` before anything that reads the raw files (`extract`, a scrape); `status` shows the counts on both sides.
- `docs/` — `WHERE_THINGS_LIVE.md` (every path git ignores, where its contents live, the jobs table), `OWNER_CHECKLIST_2026-10.md` (what only the owner can do for the jobs and the stores), `SELF_HOSTED_RUNNER.md` (the Mac mini runner, if a job board blocks GitHub's runners).
- `pipeline/store.py`, `.env.example` — the store of everything else git ignores: the `atlas-store` bucket with one manifest per store (`evals`, `caches`, `logs`; path, sha256, bytes, mtime per file). `push` uploads files whose hash changed and never deletes; `pull` writes files whose hash differs and keeps a local file that is newer than the store's copy; `status` counts local-only, remote-only and differing files; `bootstrap` is the fresh-machine command ("A fresh machine" above). `pipeline/env.py` is the one place that reads `.env`; `.env.example` lists the keys.
- `pipeline/roles_mba.py` — a second role set: the 50 roles of mbapreferred.com's "50 MBA Career Options" (consulting, strategy, finance, banking, investing, operations, marketing, sales, supply chain, HR, risk, real estate, leadership programs) plus `ai_transformation` (2026-10-30: "AI Transformation Lead", "Head of AI Transformation & Enablement", "AI Enablement Lead", "Chief AI Officer"; until then read as transformation), and, since 2026-11-05, 13 business roles Cornell Tech and IE graduates take that the 50 left out (account executive and SDR, solutions engineer, data scientist, data or business analyst, project manager, recruiter, implementation and customer experience, communications, demand generation, market research, sustainability, public policy, fraud and credit risk; `ADDED` records the day each later role joined, and a group of their own, Sustainability & policy), scraped in two batches (`--batch N` adds one batch to files that lack it). `pipeline.scrape --roles mba` runs the same adapters over the same registry with these title patterns and search queries and caches to `data/raw/jobs_mba/*.json`. Product Manager and Product Strategy Manager are the `pm` family already in `data/raw/jobs/`, Product Marketing Manager the `pmm` family and technical program managers the `tpm` family, so they are not fetched twice. The MBA set also covers employers that fit these roles but are outside the Fortune 500 and the fund portfolios (consulting firms, the Big Four, investment banks, private equity and venture firms, asset managers, regional banks, real-estate firms, consumer-goods companies): the list is `data/raw/mba_employers.json`, `pipeline.discover --list data/raw/mba_employers.json --roles mba` writes `data/raw/discovery_mba/`, and looked-up configs live in `data/raw/registry_mba_employers_*.json`. The scraper adds the verified ones for `--roles mba` only (group `mba_employer`); they are not in `data/registry.json`, so the product map does not change. An employer's category selects its title rules, its searches and its ladder; banks and investors of the Fortune list get theirs from `FORTUNE_CATEGORIES` in `pipeline/roles_mba.py`. The title rules also take campus and programme titles ("Summer Analyst", "2028 US Analyst Program"), and the analyst and associate grades that are a manager role's entry level ("Financial Analyst", "Supply Chain Analyst"); three roles have none (`NO_ENTRY_LEVEL`). `pipeline.extract --roles mba` tags them against the whole taxonomy (the shared skills plus those written for these roles, with a one-line definition each in `pipeline/depth/mba_*.json`) into `data/processed/jobs_mba.json.gz` (`pipeline/processed.py` reads and writes the processed files; one above 50 MB of JSON is kept gzipped, because GitHub refuses a file over 100 MB). Each posting gets a level on one scale and the ladder its employer uses (corporate, bank or consulting grades). Only US postings are shown; the scrape and the processed file keep every country.
- `pipeline/entry_mba.json` — the entry mark as data: which title each firm gives to MBA hires and to bachelor's hires (nine firms, each row with its source and whether the source is the firm's own), the defaults of two employer categories, and the words read in titles and posting texts. `roles_mba.entry()` reads it and gives every MBA posting three fields: `entry` (`"mba"`: a job an MBA graduate enters at; `"pre_mba"`: the same for a bachelor's or non-MBA master's graduate; `null`: an experienced-hire job or no evidence), `intern` (true for an internship, a co-op or a summer programme) and `entry_src` (`title` or `text`: the posting says who it is for; `firm` or `category`: the title is the grade that group joins at). Levels are not changed by the mark: an MBA joins McKinsey at `mid`, Deloitte at `senior`, and "Associate" is the bachelor's grade at BCG. The fields are in `data/processed/jobs_mba.json` and in the role files; `roles.<role>.entry` and `ladders.<ladder>.entry` in the index count them per ladder; the table is copied into `web/data/roles_mba.json` under `entry`, and `evals/roles_mba.mjs` reads it the same way (`R.entry(title, who, {text, yoe})`).
- `pipeline/sponsorship.py`, `pipeline/sponsorship.json` — visa sponsorship as a posting fact, not a skill (PLAN.md v16, step 8). `extract` gives every posting of both sets `sponsorship`: `"yes"` when the text says the employer sponsors ("visa sponsorship is available", "will sponsor", "H-1B sponsorship"), `"no"` when it says it does not ("unable to sponsor", "not eligible for visa sponsorship", "must be authorized to work without sponsorship"), else `null`; the patterns are data, anchored on visa, immigration and work-authorization words so a project sponsor or a sponsored event never counts, and a no wins over a yes. - `pipeline/jobs_open.py`, `web/jobs.js`, `web/data/jobs_open.json`, `web/data/jobs_meta.json` — Find jobs, one search over every open posting (v19, step B4). `.venv/bin/python -m pipeline.jobs_open` reads `graph.json` and `graph_mba/<role>.json` after a build (no network, no `.env`) and writes `jobs_open.json`, column-oriented so the screen loads it fast (7.4 MB raw, 1.8 MB gzipped): `companies` (`name`, `group`, `sector`, `url_prefix`), `locations`, `roles` and `role_labels`, `titles` and `skill_ids` (the union of both sets') are lists, and each of `rows` is `[num, companyIdx, roleIdx, titleIdx, levelIdx, locationIdx, flags, skills, url, firstSeen]`: the id is `p<num>` or `m<num>`, `role` is the site's role id (`product.<family>` for the product set), `levelIdx` indexes `levels[set]`, `flags` is a bit field (`flags` in the file names the bits: MBA set, internship, remote, MBA entry, bachelor's entry, sponsors yes or no), `url` follows the company's `url_prefix`, `firstSeen` stays null until the role files carry it; no snippet, no sub-skills. `jobs_meta.json` is the counts alone, which home reads. `jobs.js` is the pure logic of the screen and loads in node (`require("web/jobs.js")`): `rowsOf` (the file expanded once into row objects), `searchJobs` (words AND; a whole word 2, a prefix 1; title 3, company 2, role name 2, skill name 1, location 1), `filterJobs` and `facetCounts` (each value's count with the other filters as they are), `fitOf` and `fitLine` ("N of the M skills", never a percentage), `sortJobs` (best, fit, company), `dedupe` (title, company, location), `pageOf` (50), `parseState` and `stateQuery` (the hash), and `LEVEL_WORDS`, which folds each set's eight level ids to the rail's four words (senior with Manager, group with Lead or principal, VP and chief officer with Director). The screen hands it a `ctx` with `roleName`, `skillNames` and `fieldOf`, so the module holds no data. `tests/web/jobs.test.mjs` covers each function on synthetic rows and checks the real file against the indexes.
- `pipeline/catalog_export.py`, `pipeline/catalog_tags.mjs`, `web/data/catalog/` — the catalog as public files (v19, step B3). `.venv/bin/python -m pipeline.catalog_export [path to SP27_cornell_tech]` runs the course catalog's own loader in its dry-run mode (no network, no `.env`) and writes `web/data/catalog/cornell_tech.json` (committed: the rows the picker reads, the same columns as `catalog.js` selects) and `web/data/local/catalog_full.json` (gitignored, this machine only: the same rows plus `roster_syllabus_md`). The public file never holds the syllabus digest or the research note; the export asserts it. `node pipeline/catalog_tags.mjs` reads the local file, runs `Atlas.readCourse` over `Catalog.matcherText` per class code and writes `web/data/catalog/cornell_tech_tags.json` (`found` and `teaches` per code; a skill stays only when the text names it, a sub-skill hint alone does not count). The tags file carries the sha256 of `web/data/taxonomy_mba.json` and `web/data/taxonomy.json`, and `tests/web/catalog_files.test.mjs` fails when either hash is stale: rerun the tags after any taxonomy change.
- `evals/` — evals and baselines: sample resumes with expectations and `node evals/run.mjs` for the matcher; `node evals/rough_fit.mjs` for the interface's rough read of a resume against the full matcher on every MBA role (report in `rough_fit.md`); `extraction_baseline.md` for the product taxonomy (regex vs model judgment on 200 postings); `extraction_baseline_mba.md` for the MBA role set (what each role's postings ask for, per skill and per role); `run_pipeline.py` for the MBA data layer (labelled titles, levels, entry marks and countries, golden postings, integrity of the graph files; baseline in `pipeline_baseline_mba.md`); `run_depth.py` for the published skill depth (shape, style, specificity, evidence, ladder order, sub-skill shares, build steps; baseline in `depth_baseline_mba.md`); `NOTES.md` for the design history and findings.
- `pipeline/experiments/` — taxonomy tooling. For drafting skills from postings: `role_corpus.py` (cleaned postings of a role set), `role_terms.py` (phrases that set a role apart), `skill_probe.py` (try draft skills on postings and read what matched).
