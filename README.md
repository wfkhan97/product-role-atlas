# Product Job Map

An interactive map of what product roles actually ask for, built from live job postings at the
Fortune 50 and at a16z- and Sequoia-backed startups. Pick a role family and level, click around the
skill graph, or drop in a resume / course list to see how well you match a specific posting.

See [PLAN.md](PLAN.md) for the design.

## Run it

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # requests, beautifulsoup4, pypdf, psycopg
.venv/bin/python -m pipeline.backlog pull   # the raw postings from the Supabase backlog -> data/raw/jobs*/ (SUPABASE_DB_URL in .env)
./run_all.sh            # merge registry, scrape (cached per company), extract, build graph; log in logs/run_<date>.log
./run_all.sh --refresh  # fetch every board again and merge into the backlog (--force is the old name)
.venv/bin/python -m pipeline.scrape --roles mba --refresh   # weekly: the MBA backlog (several hours; add --ats workday or --only "Name" to narrow)
.venv/bin/python -m pipeline.discover --from 101 --to 250   # (re)discover careers sites for a rank range
.venv/bin/python -m pipeline.scrape --rank-from 101 --rank-to 250   # scrape one Fortune tier
.venv/bin/python -m pipeline.scrape --roles mba   # same companies plus role-specific employers, the 50 MBA roles -> data/raw/jobs_mba/
.venv/bin/python -m pipeline.extract --roles mba  # tag the MBA postings -> data/processed/jobs_mba.json.gz (about 20 minutes)
.venv/bin/python -m pipeline.build_graph --roles mba  # the MBA graph -> web/data/graph_mba.json + web/data/graph_mba/<role>.json
.venv/bin/python evals/run_pipeline.py            # evals for titles, levels, countries, golden postings and the graph files
.venv/bin/python evals/run_depth.py               # content evals for the published skill depth (style, specificity, evidence, build steps)
.venv/bin/python -m pipeline.funnel --from 2026-10-31 --to 2026-11-07   # the capture funnel: sessions, the share reaching each screen, waitlist rows (CAPTURE_DB_URL in .env)
cd web && python3 -m http.server 8000   # then open http://localhost:8000
```

## Tests and logs

`node --test 'tests/web/*.test.mjs'` checks the browser code and `.venv/bin/python -m pytest tests/python` the
pipeline (`pip install -r requirements-dev.txt` once); both finish in about a second and never touch the network.
`tests/README.md` says what a test is and what an eval is. Every stage logs through `pipeline/log.py`: INFO lines
per stage with counts and elapsed seconds, WARNING for a skipped record or a partial fetch, ERROR with the traceback
for a failed employer, all on stderr; stdout stays as it was. `./run_all.sh` also writes the log to
`logs/run_<date>.log` (gitignored) and prints the path at the end; any stage does the same when `PIPELINE_LOG` names a
file, and `PIPELINE_LOG_LEVEL=DEBUG` shows more. API keys never appear in a log line: the values in `.env` are masked.
CI (`.github/workflows/ci.yml`) runs both test suites, `node evals/run.mjs` and `evals/run_pipeline.py` on every pull
request and on `main`.

## Scratch versus documentation

Interim work (plans under review, mockups, audits) lives under `data/experiments/scratch/<topic>/` (gitignored) or the
session scratchpad, never in the tree; `./sweep_scratch.sh --go` moves it to `data/experiments/_trash/<date>/` at the
end of a thread. What lasts goes here (what exists, how to run it) and in `PLAN.md` (the decisions and why). The rule is
in `CLAUDE.md`.

## Layout

- `pipeline/adapters/` — one module per ATS (Greenhouse, Lever, Ashby, Workday, Eightfold, Phenom, Oracle HCM, SmartRecruiters, Amazon, Apple, Google). Two adapters read boards that only the MBA employers use. `talnet.py` reads tal.net (Oleeo) boards from their public Atom feed (`…/candidate/jobboard/vacancy/<n>/feed/structured`, the whole board in one answer). A firm has several boards (experienced hires, students, regions), so the config names them: `{"host": "lek.tal.net", "boards": [{"name": "Americas", "path": "appcentre-2/brand-2", "vacancy": 3}, …]}`. When the firm puts the description in the feed (CohnReznick) it is taken from there; otherwise each vacancy page is read (L.E.K.). Some tal.net sites put their vacancy pages behind a captcha (Evercore): the adapter does not pass it, says so on stderr and returns nothing for those postings. `yello.py` reads Yello (recsolu.com) boards (Kearney): the board page names its search URL, the search answers 25 cards a page, the whole board is listed and filtered by title, then each job page is read; the list shows an age or a day without a year, so `posted` is approximate. Configs for both are in `data/raw/registry_mba_employers_talnet_yello.json`.
- `pipeline/roles.py` — which titles count as product roles; family / level / specialisation classification.
- `pipeline/taxonomy.json` — the skill taxonomy (clusters, skills, regex patterns): one vocabulary for every role set. A skill marked `"only": ["mba"]` belongs to that role set alone; unmarked skills are shared. A shared skill may carry `"patterns_for": {"mba": [...]}`: stricter wording for that role set, where a word that means the skill in product postings is said in passing. `pipeline/tax.py` hands each role set its part, and `build_graph` writes the product part to `web/data/taxonomy.json` for the web app and the evals. Patterns are tuned for precision against model judgments on a 200-posting sample (see `evals/extraction_baseline.md`); avoid bare everyday words. Every skill also carries a `kind` (`pipeline/tax.py`, `KINDS`): `method` (a craft with an artefact: PRDs, valuation, S&OP), `practice` (work through people: stakeholders, programmes, partnering), `behaviour` (asked by every field, shown through other work, never named: communication, ownership, influence), `technical`, `knowledge` (industries and rule sets), `tool`, `credential`. The kind says nothing to extraction; it decides how a resume shows the skill and how the interface should treat it.
- `pipeline/evidence.json` — how a resume shows each of the 278 skills, hand-written: the `form` (`through` other work, `scope`, `artefact`, `outcome`, `built`, `context`, `named`), the `artefacts`, `counterparts`, `measures` and `verbs` a line that shows it carries, and `shown_by`, the concrete skills whose evidence counts for a behaviour or a practice. `pipeline/fields.json` — what the 24 skills that four or more of the 11 fields ask for mean in each field that asks: `reads_as` (one sentence), `shown_by` (the field's own skills that carry it; each must co-occur with the skill in at least 15% of the field's postings that ask for it) and `line` (one resume line in the field's words, with a number). `tax.validate` checks both files; `evals/run_taxonomy.py` checks them against the postings. The graph build publishes `kind`, `how_shown` and `fields` on every skill node (the field entries with the postings' own carriers and sub-skill mix beside them) and the kinds table in `meta.kinds`.
- `pipeline/depth/*.json` — editorial depth per skill: plain-English definition, sub-skills (with regex patterns and examples), a four-step level ladder, how to build it, and resume lines that show it. Sub-skills are also tagged in postings and used for partial credit in the matcher. The product files were written by hand. The MBA files (`mba_*.json`) are written by `pipeline.depth_publish` from posting evidence: `ladder` is keyed by industry ladder first (`{"bank": {"associate": ..., "mid": ...}}`, corporate, bank and consulting rungs differ), `build` by ladder too (`{"bank": [{kind, text, target, source, url, grounding, demand}]}`), and `provenance` holds, for every statement, sub-skill and step, the posting ids, employers, quoted phrase and cited sentences it rests on, and the reason of every empty rung. A rung that the postings do not support is absent, never padded; a ladder with one rung is not shown. The skill card on a role screen shows the role's own industry ladder, with that ladder's level names; when it is not written for the skill, another industry's, labelled as such. `mba_roles.json` holds per role and ladder the licences, exams and degrees that five employers name at entry level (`asks`) and the steps a source grounds (`build`); the graph build copies them into `roles.<role>.depth` of the index.
- `pipeline/scrape.py`, `extract.py`, `build_graph.py` — the three stages. `scrape`, `extract` and `build_graph` take `--roles product|mba`; scrape and extract share one code path (title filter, cleaning, repost and repeated-URL dedupe, tagging in worker processes). The web app is product-only for now. Extract also pulls evidence sentences per skill and level group; build_graph computes the axis positions (seniority = share-weighted level centre of mass; IC vs leads-teams = director+ share vs staff/principal share; commercial vs technical = PMM/growth share vs TPM/platform share), rank-spread with shrinkage for rare skills.
- `data/raw/fortune500_2026.json` — the 2026 Fortune 500 with Fortune's industry labels; `pipeline/sectors.json` groups those 66 industries into 11 sectors for the Industry filter.
- `pipeline/discover.py` — automatic careers-site discovery for Fortune companies (domain via Clearbit/Wikipedia, careers-link crawl, ATS signature detection, Workday tenant guessing, adapter verification). Output in `data/raw/discovery/`. Companies it can't resolve are handed to research agents, whose results land in `data/raw/registry_fortune_agents_*.json`.
- `pipeline/verify_one.py` — verify a single ATS config with the real adapter.
- `data/raw/funds.json` — the 52 venture funds (institutional, corporate and YC) whose portfolios feed the startup side; `data/raw/portfolio_<fund>.json` are the scraped portfolio lists (name, website, status, stage where the fund states it).
- `pipeline/probe_startups.py` — for every active portfolio company, finds a Greenhouse / Lever / Ashby board (slug guessing plus a careers-page scan), keeps those with product postings, and writes `data/raw/registry_startups.json` with each company's list of backing funds. Stage: fund-stated Seed/Series letters are kept; otherwise it is inferred from the company's own postings ("we raised our Series B") in `pipeline/extract.py`.
- `data/raw/registry_*.json` — per-company ATS configs; `pipeline/merge_registry.py` merges them (hand-verified > agents > auto) with Fortune tier, industry and sector into `data/registry.json`. One job board is one employer: startups that fund portfolios list under two names are merged (other names kept in `also_listed_as`).
- `data/raw/jobs/*.json`, `data/raw/jobs_mba/*.json` — raw postings per company. Each file is a backlog, not a snapshot: a refresh never drops a posting. One the board still shows gets a new `last_seen`; a new one is added with `first_seen`; one the board no longer shows gets `closed` (the day we first missed it). A posting is its requisition id (`external_id`), or its URL on a board that gives none: Bank of America puts a per-session token in every job URL, and a retitled or moved requisition gets a new URL, so the URL alone is not stable. One that comes back takes the board's current title, URL and text. If a refresh returns under 30% of the postings that were open, nothing is closed (the board or a search failed) and the file says `partial`. For the MBA set a closed posting stays in the statistics for 12 months after it was last seen (`KEEP_CLOSED_DAYS` in `pipeline/extract.py`) and carries `open: false` into the graph, so the interface can leave it out of listings. The product set drops closed postings until its interface can hide them.
- `pipeline/backlog.py` — the store of the raw posting files: the `backlog_files` and `postings` tables of the GradBuddy Supabase project. `data/raw/jobs/` and `data/raw/jobs_mba/` are not in git (over 350 MB together, and every refresh rewrites every file; the history before 2026-10-19 still holds them). `push` sends the files (the scrape pushes each file as it writes it when `SUPABASE_DB_URL` is set), `pull` writes them back byte for byte, `verify` proves the round trip, and a full scrape keeps the newest four dated gzipped snapshots in the `backlog` storage bucket. Push never deletes a posting and pull never overwrites a local posting the database lacks. `.env` holds `SUPABASE_DB_URL` (session pooler) and `SUPABASE_SERVICE_ROLE_KEY` (snapshots). A fresh machine runs `pull` before anything that reads the raw files (`extract`, a scrape); `status` shows the counts on both sides.
- `pipeline/roles_mba.py` — a second role set: the 50 roles of mbapreferred.com's "50 MBA Career Options" (consulting, strategy, finance, banking, investing, operations, marketing, sales, supply chain, HR, risk, real estate, leadership programs), scraped in two batches (`--batch N` adds one batch to files that lack it). `pipeline.scrape --roles mba` runs the same adapters over the same registry with these title patterns and search queries and caches to `data/raw/jobs_mba/*.json`. Product Manager and Product Strategy Manager are the `pm` family already in `data/raw/jobs/`, Product Marketing Manager the `pmm` family and technical program managers the `tpm` family, so they are not fetched twice. The MBA set also covers employers that fit these roles but are outside the Fortune 500 and the fund portfolios (consulting firms, the Big Four, investment banks, private equity and venture firms, asset managers, regional banks, real-estate firms, consumer-goods companies): the list is `data/raw/mba_employers.json`, `pipeline.discover --list data/raw/mba_employers.json --roles mba` writes `data/raw/discovery_mba/`, and looked-up configs live in `data/raw/registry_mba_employers_*.json`. The scraper adds the verified ones for `--roles mba` only (group `mba_employer`); they are not in `data/registry.json`, so the product map does not change. An employer's category selects its title rules, its searches and its ladder; banks and investors of the Fortune list get theirs from `FORTUNE_CATEGORIES` in `pipeline/roles_mba.py`. The title rules also take campus and programme titles ("Summer Analyst", "2028 US Analyst Program"), and the analyst and associate grades that are a manager role's entry level ("Financial Analyst", "Supply Chain Analyst"); three roles have none (`NO_ENTRY_LEVEL`). `pipeline.extract --roles mba` tags them against the whole taxonomy (the shared skills plus those written for these roles, with a one-line definition each in `pipeline/depth/mba_*.json`) into `data/processed/jobs_mba.json.gz` (`pipeline/processed.py` reads and writes the processed files; one above 50 MB of JSON is kept gzipped, because GitHub refuses a file over 100 MB). Each posting gets a level on one scale and the ladder its employer uses (corporate, bank or consulting grades). Only US postings are shown; the scrape and the processed file keep every country.
- `pipeline/entry_mba.json` — the entry mark as data: which title each firm gives to MBA hires and to bachelor's hires (nine firms, each row with its source and whether the source is the firm's own), the defaults of two employer categories, and the words read in titles and posting texts. `roles_mba.entry()` reads it and gives every MBA posting three fields: `entry` (`"mba"`: a job an MBA graduate enters at; `"pre_mba"`: the same for a bachelor's or non-MBA master's graduate; `null`: an experienced-hire job or no evidence), `intern` (true for an internship, a co-op or a summer programme) and `entry_src` (`title` or `text`: the posting says who it is for; `firm` or `category`: the title is the grade that group joins at). Levels are not changed by the mark: an MBA joins McKinsey at `mid`, Deloitte at `senior`, and "Associate" is the bachelor's grade at BCG. The fields are in `data/processed/jobs_mba.json` and in the role files; `roles.<role>.entry` and `ladders.<ladder>.entry` in the index count them per ladder; the table is copied into `web/data/roles_mba.json` under `entry`, and `evals/roles_mba.mjs` reads it the same way (`R.entry(title, who, {text, yoe})`).
- `pipeline/geo.py` — the country reader for role sets that show one country (the MBA set). It reads "US - Remote", country codes, lists of sites and, for SuccessFactors boards, the city in the posting URL. The product map keeps `extract.geo` until its baselines are rerun.
- `pipeline/balance.py` — company-balanced shares: one employer counts for at most 5% of a role. Used by the MBA graph and by `role_coverage.py`.
- `pipeline.build_graph --roles mba` — the MBA graph, US postings only. `web/data/graph_mba.json` is the index: roles, groups, levels and the names of each level per ladder, skills with company-balanced shares per role, and per role the skills that define it (`defining`) apart from what it asks beyond that (`asks`). `web/data/graph_mba/<role>.json` holds one role's postings, loaded on demand; `_evidence.json` there holds example sentences per skill. The index plus the postings of the roles loaded has the shape of `graph.json` (`evals/graph_mba.mjs` shows how), so `web/match.js` reads it unchanged. `web/data/taxonomy_mba.json` and `subskills_mba.json` are the MBA part of the taxonomy for the matcher.
- `web/data/roles_mba.json` — the MBA title rules as data, for code that runs in the browser: each role's label, group, title patterns (JavaScript regular expressions), the roles it covers, employer rules, and the grade patterns and level names of each ladder. Written by the graph build from `pipeline/roles_mba.py`; `evals/roles_mba.mjs` is a reference reader.
- `pipeline/depth_gen.py`, `pipeline/build_steps.py`, `pipeline/build_sources.py`, `pipeline/depth_publish.py` — skill depth of the MBA skills, from postings. `depth_gen` drafts sub-skills and ladder rungs from posting sentences with one model (`openai/gpt-6.1-sol`) and keeps what code checks and a second model of another family (`anthropic/claude-haiku-5.5`) support: every statement of a rung is asked for by two employers, quotes its evidence, names terms of it, passes a style check, differs from the rung below, and is read as its own skill and level when shown alone; `--report` writes the release report of a run. `build_steps` writes "how to build it" steps on two keys: a target that postings name (a document that three employers name in the skill's sentences, or five elsewhere in the posting; a licence, exam or degree that five employers name for a role) and a source on the allow-list that says what the target contains (`data/raw/build_sources.json`: US government, regulators, certification bodies; the last two are named and linked, never quoted; course vendors are never named). Steps fill templates; a step on a passage that only names a public input is labelled "input only"; a ladder on hold in the registry (consulting) gets none. `build_sources verify` hashes every source record, fetches the ones a script may read (PDFs with pypdf) and marks each stored passage found or not. `depth_publish` writes the checked content into `pipeline/depth/mba_*.json`. The model steps need `OPENROUTER_API_KEY` in `.env`, cache every answer in `data/experiments/depth/` (a rerun sends only what is missing; the cap counts answered requests) and have a `--dry-run` that states the cost. Findings in `evals/NOTES.md`; checks on the published files in `evals/run_depth.py`.
- `web/` — the static site, no build step. `index.html` is the shell (top bar with breadcrumbs, a main column, a side
  panel, a footer). `atlas.js` is the data layer: both role sets behind one interface (`Atlas.index()` the fields and
  roles, `Atlas.product()` the product set from `data/graph.json`, `Atlas.role(id)` one role's postings, skills,
  sub-skills and evidence, `Atlas.grid()` the skill grid). `app.js` is the screens on hash routes: `#/` the first
  visit (tell us about you, or explore), `#/explore` the fields as cards (the ones that fit first) or as the skill map, `#/field/<group>`
  the roles of a field on the left and the field's skills on lanes on the right (`SkillMap.chart`), `#/role/<role>`
  the role screen (one sentence on the job from `web/data/role_blurbs.json`; the skills by area; level and employer-type
  chips, with industry, employer and location behind "Filters", every count reflecting the other filters; the rail
  on the right with the legend, the person's fit or the resume drop zone, and what to do with the role; a skill or
  posting card draws over the rail; under 1180 px the rail is an edge tab and an overlay), `#/you` the three questions (what you study, where you are in your search, which fields) and the optional
  resume (answers and resume stay in the browser's local storage; `Atlas.roughFit` ranks fields and roles from the
  index alone), `#/role/<role>/fit` the fit screen (the matcher built as the bands were calibrated, `Atlas.matcher`,
  read once per view by `computeFit` for the rail and this screen; the band from `bands.json` or `bands_mba.json` on
  a four-step scale, never a percentage; plain words for a group with no bands; the two columns of what the resume
  shows and what needs more evidence), `#/role/<role>/course` (drop or paste
  a syllabus; `Atlas.readCourse` names the skills it mentions; the grid shows what the course teaches and what most
  postings ask for that it does not name), `#/field/<group>/event?networking|roundtable|hackathon` (who is in the
  room and what to ask, what to say about yourself, employers hiring now from the field's postings
  (`Atlas.fieldJobs`); role by role what to bring up with the resume line that shows it; what to build from the
  skills most roles ask for that the resume does not show), `#/about`. `skillmap.js` draws Explore as a skill map (the fields on a ring, every skill near the fields that ask for it, lines where postings ask for two together; the 35 most-asked skills solid and named, the rest faint and named by a lens around the pointer; with a resume, green for the skills the person's roles ask for that the resume shows and blue for the gaps; a skill opens a short card of the roles and fields that ask for it), with a switch back to plain cards, and `SkillMap.chart` draws one field's skills on lanes for the field page. The MBA set's "Product" group is not shown: the Product field
  opens the product role set, whose six families have the richer depth content. The skill grid has rows by how many
  postings ask for a skill (over half, a quarter to a half, one in ten to one in four) and two columns (asked at
  every level, or at least 1.5 times as often in leadership postings as in entry ones, measured over the whole
  role); skill areas are text labels; ◆ marks a role's defining skills. Closed postings count in every share and are
  never listed. Desktop only. `web/data/bands.json` and `web/data/bands_mba.json` (written by `evals/calibrate.mjs`)
  hold the bands of fit and the scoring they were calibrated with. `atlas.js` also loads in node (`require("web/atlas.js")({ load, Matcher })`) so the evals can run the same code.
- `games/` — design packages for the games on the first-visit screen, one folder per game (how it works, a build prompt, high-fidelity mocks and a cover image); `games/README.md` is the index. Five games since v12: Know the role (pick a role's real asks, call skills over or under half; it merged Higher or lower, What does it ask for and Build the hire, whose packages stay as history), Guess the role, Spot the real ask, Climb the ladder, Where's the demand, plus Skill path. The first screen shows the game cards as one carousel row in the order of the facts they teach (what a role asks for, how postings read, what senior means, where the jobs are, how skills link), each card naming its fact, one marked "Start here", each opening on the player's default role; the list, the groups and the card copy are `web/data/games.json`. A role screen's "Practise" and the fit page's "Practise your gaps" open a round on that role. The built games (`web/games/`) share one shell, `web/gameshell.js`: one header, one key convention, one end-screen template and one `localStorage` record (PLAN.md, "The games, second pass (v12)").
- `web/tokens/` — the GradBuddy design tokens (CSS custom properties, oklch, dark and light), copied verbatim from the design-system snapshot of 2026-10-09; `web/style.css` is written on them and look changes go through tokens only. The theme follows the device unless overridden from the top bar.
- `web/capture.js`, `pipeline/sql/`, `pipeline/funnel.py` — capture (PLAN.md, "The demand-gen pass", step 1). `capture.js` is a classic script loaded before `app.js`: `Capture.event(name, ctx)` posts one funnel event (a name from a closed list, a random per-browser-session id from `sessionStorage`, the stage, the program group, a role or field id) and `Capture.waitlist(email, source, ctx)` one waitlist row (the email, where the click was, the role on screen, the stage, the program group, the fields picked) to the `gradbuddy-catalog` Supabase project with the publishable key; every error is swallowed, and `CONFIG.CAPTURE_ENABLED: false` makes both no-ops. Nothing a person types or drops leaves the browser: no resume, syllabus, pasted posting, skill id or file name, ever. `pipeline/sql/2026-10-25_capture.sql` creates the two tables (row-level security, anonymous insert only, a unique index on `lower(email), source` so a second click is not a second row); the owner applies migrations by hand, never a thread. `pipeline.funnel` prints the funnel for a date range (sessions, the share that reached each event, by stage and by program group, waitlist rows by source); it reads `CAPTURE_DB_URL` from `.env` (the catalog project's session-pooler string), else `SUPABASE_DB_URL`.
- `web/evidence_text.js` — every sentence a screen shows about a skill, built from the data (PLAN.md v14, decision 2): the example line (the role's field entry, else the product skill's `signals`, else a template from `how_shown` with no number invented), what the skill means in the field, the gap sentence by kind, the measures to add, and one sentence for a skill with no field entry. Pure logic, loaded in the browser and required by node; `evals/adaptive.mjs` checks it over every role.
- `web/match.js` — the resume matcher (pure logic, no DOM): per-line evidence with strength, tiered requirements, persona and level read, transfer vocabulary, and skills presumed from a role the person held at or above the target level (part credit, shown apart from evidence). A behaviour (kind) is a row credited through its carriers (`pickCarriers`: the skills of a carrier kind its evidence entry and the role's field entry name, re-ranked on the role's postings), status `through`; naming it earns nothing. `createMatcher({ behaviours })` is `"show"` (weight 0) or `"score"`, as the bands files record under `scoring`. Used by `app.js` and by the evals. It reads the role family of each job title from a list passed in as `roles` (for the MBA role set: `web/data/roles_mba.json`, written by the graph build); the product families are built in.
- `web/catalog.js`, `web/classes.js`, `web/config.js`, `web/data/sp27_campus.json` — the Spring 2027 class picker (`#/classes`), the professor card (`#/professor/<slug>`) and sign-in (`#/signin`), read from the `gradbuddy-catalog` Supabase project with the publishable key in `config.js` (row-level security: signed-in cornell.edu accounts read the catalog tables and nothing else). `catalog.js` is the client, the reads and the pure functions (cross-list collapsing, grading chip, eligibility filter, relevance band, a minimal markdown reader); it loads in node (`require("web/catalog.js")({})`) for `tests/web/classes.test.mjs`. `classes.js` draws the screens; app.js only dispatches to it. Every Cornell-Tech-specific string (eligibility words, programs and what they may enroll in, the relevance thresholds, the pre-enrollment dates) is data in `sp27_campus.json`. `CONFIG.AUTH_ENABLED` is the launch switch: it shows the top-bar "Sign in" and makes `#/classes` demand a session; `#/signin` always works. The student's program, chosen role and own ratings stay in localStorage (`classes.program`, `classes.role`, `classes.own`); the prior-term syllabus digest is matcher input and is never shown.
- `evals/` — evals and baselines: sample resumes with expectations and `node evals/run.mjs` for the matcher; `node evals/rough_fit.mjs` for the interface's rough read of a resume against the full matcher on every MBA role (report in `rough_fit.md`); `extraction_baseline.md` for the product taxonomy (regex vs model judgment on 200 postings); `extraction_baseline_mba.md` for the MBA role set (what each role's postings ask for, per skill and per role); `run_pipeline.py` for the MBA data layer (labelled titles, levels, entry marks and countries, golden postings, integrity of the graph files; baseline in `pipeline_baseline_mba.md`); `run_depth.py` for the published skill depth (shape, style, specificity, evidence, ladder order, sub-skill shares, build steps; baseline in `depth_baseline_mba.md`); `NOTES.md` for the design history and findings.
- `pipeline/experiments/` — taxonomy tooling. For drafting skills from postings: `role_corpus.py` (cleaned postings of a role set), `role_terms.py` (phrases that set a role apart), `skill_probe.py` (try draft skills on postings and read what matched). For checking them: `role_coverage.py` (writes `evals/extraction_baseline_<roles>.md`) and `skill_audit.py` (model judgment on sampled tagged and untagged postings per skill). The product model-judgment audit is `decisions_audit.py`, `decisions_report.py`, `decisions_compare.py`. Needs `OPENAI_API_KEY` in `.env` for a live run; `--reuse` recomputes the regex side against saved answers without API calls. Output lands in `data/experiments/` (gitignored).
